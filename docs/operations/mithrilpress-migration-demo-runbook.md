# MithrilPress synthetic migration demo runbook

This runbook demonstrates the current WordPress-supported subset with synthetic
content on a local Worker, local D1, and local R2 emulator. It does not read or
contact a prospect website, send email, deploy Cloudflare resources, create DNS,
or publish a public preview.

## Scope and fixture

The fixture generator creates the fictional **Northstar Fictional Services**
site: 24 pages, 6 posts, categories, tags, nested page paths, 10 deterministic
original PNG illustrations, and deliberate unsupported-content examples. The
WXR includes a custom post type, a password-protected page, a dynamic Gutenberg
block, a custom field, and attachment metadata so the owner can inspect the
omission report. The image files are generated by
`apps/mithrilpress-worker/scripts/migration-demo-fixtures.mjs`; no third-party
or prospect content is used.

## Local setup

From the repository root, verify the selected checkout is clean and current
before doing setup. Then use only the example Wrangler config and its local
state:

```sh
cd apps/mithrilpress-worker
npm ci
npm run build:mithril
npx wrangler d1 migrations apply mithrilpress --config wrangler.example.jsonc --local
umask 077
npm run provision:site -- --target local --config wrangler.example.jsonc \
  --database mithrilpress --hostname demo.sites.mithril.love \
  --owner-label "Northstar demo owner" --source-origin https://northstar.example \
  > /private/path/provisioned-site.json
npm run dev -- --ip 127.0.0.1
```

Save the one-time provisioning JSON to a private file outside the repository
with `umask 077`. Keep its `owner_token` in an owner-only token file, and its
`site_id` for the demo command. The provisioned owner token has preview,
approval, publication, and media scopes, but does not grant WordPress import.
For example, when the provisioning response is saved as
`/private/path/provisioned-site.json`:

```sh
jq -r '.owner_token' /private/path/provisioned-site.json > /private/path/owner.token
jq -r '.site_id' /private/path/provisioned-site.json
chmod 600 /private/path/owner.token /private/path/provisioned-site.json
```

Create a separate short-lived importer token with the two required scopes:

```sh
umask 077
node scripts/create-owner-token.mjs "Northstar demo importer" content:import media:write > /private/path/import-token.json
jq -r '.token' /private/path/import-token.json > /private/path/importer.token
chmod 600 /private/path/import-token.json /private/path/importer.token
npm run token:import:local -- --site-id <local-site-id> --token-json /private/path/import-token.json
```

The local-only command verifies that the JSON contains exactly the
`content:import` and `media:write` scopes, inserts only the salted hash material,
and reads the row back before reporting success. The bearer token is never sent
to D1 or printed by that command. Keep both JSON and token files outside the
repository; do not use a remote target or production config.

## Run the walkthrough

Choose a new output directory whose parent already exists. The runner refuses
to overwrite an existing directory and accepts only loopback HTTP targets.

```sh
npm run demo:migration -- \
  --site-host demo.sites.mithril.love \
  --site-id <local-site-id> \
  --import-token-file /private/path/importer.token \
  --owner-token-file /private/path/owner.token \
  --output-dir /private/path/mithrilpress-demo-20261023
```

For each revision, the runner saves a machine-readable migration report and an
authenticated `noindex` preview. Review both files and type the exact revision
ID to approve it. It asks separately before publication. After publishing the
update, it asks for both the historical target ID and the current revision ID
before restoring. It then reads the current publication snapshot from the local
control hostname and checks the public page content against the restored
revision.

The resulting directory contains:

| Artifact | Evidence |
| --- | --- |
| `first-migration-report.json`, `update-migration-report.json` | Import subset, parity decision, sanitization and omission counts |
| `first-private-preview.html`, `update-private-preview.html` | Owner-authenticated `noindex` preview outputs |
| `publication-first.json`, `publication-update.json` | Read-back of each separately approved publication |
| `publication-first.html`, `publication-update.html` | Public route read-back for the first and updated revisions |
| `publication-restored.json`, `publication-restored.html` | Read-back after restoring the first publication |
| `demo-receipt.json` | Synthetic fixture identity, exact revision IDs, and final snapshot digest |

Open the saved private and public HTML at desktop and mobile viewport sizes for
the required owner/reviewer journey. The preview files contain only synthetic
content and stay in the selected local output directory.

## Expected decisions

The report should reconcile 24 imported pages and 6 imported posts. It should
also show the unsupported post type, protected page, source metadata and media
handling, and the dynamic-block review requirement. The overall
`parity_status` is expected to be `owner-review-required` because the fixture
deliberately contains unsupported source material. That is a review outcome,
not a failure and not a claim of full WordPress parity.

Approval and publication are separate owner actions on exact revision IDs.
Restore accepts only a different historical revision that was previously
published, still has its original approval, and is complete. The restore action
is recorded separately in the owner-action log. Export read-back is the
owner-authenticated publication snapshot containing the supported content,
taxonomy, and media metadata.

## Stop conditions

Stop if the Worker target is not loopback, the source origin differs from the
fictional fixture origin, any fixture is missing, the report/revision counts do
not reconcile, a private preview can be read without owner authorization, or a
publication snapshot returns a different revision than the selected action.
Keep the revision private and record the exact error code for follow-up.

This demonstration does not qualify a production Worker, provider-level cost
stop, DNS/TLS, public route, managed service, or any campaign. Those gates
remain tracked independently in Linear.
